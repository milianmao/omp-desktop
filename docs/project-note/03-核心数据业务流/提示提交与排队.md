# 提示提交与排队

用户按下发送后，消息可能立刻进入 omp，也可能进入 steer/follow-up 队列。这个分叉是项目里最容易被改错的一处：**通道选错，命令就变成普通文本**。

## 触发点

| 触发 | 位置 | 条件 |
|---|---|---|
| Enter / Ctrl+Enter | `design/composer.jsx` | 按键由 `window.isSubmitKey(e, submitKey)` 判定（Settings → Composer） |
| 队列条 ↑ / ⚡ | `design/queue-strip.jsx` | ↑ 仅 follow-up；⚡ 仅 agent 运行中 |
| 队列条 ✕ / ✎ | 同上 | ✎ 仅在 `removed: true` 后回填文本 |
| 计划批准 | `app-live.jsx:582` 的 `bridge.followUp(APPROVAL_PROMPT)`（`constants.js:76`） | 走 follow-up 通道 |
| goal 首条 objective | `use-goal-mode.jsx` → `OMP_BRIDGE.goalStart` | goal 已创建但 omp 未自行开跑 |
| 手机端 | `app/remote-view.js` 动作执行器 | 经 `OMP_BRIDGE` 同一入口 |

## 数据流路径

```
composer 提交
  → OMP_SLASH.routeSubmit(cmds, text, {goalMode, followUp, streaming, connected})
        app/slash-commands.js:343
     └ 返回 { isCmd, via }：
        via = goal | followUp | steer | prompt | local
  → 按 via 分支（live.js）
     ├ prompt   → _sendWithResponse({type:"prompt", message, images})
     ├ steer    → _sendQueued("steering", …)   live.js:3152
     ├ followUp → _sendQueued("followUp", …)   live.js:3321
     └ goal     → 不 unsettled 时走 prompt；unsettled 时进队列但帧仍是 prompt+streamingBehavior
  → 帧构造 OMP_SLASH.queuedFrame(kind, text, images, isCmd)   slash-commands.js:361
        isCmd  → { type:"prompt", message, images, streamingBehavior: kind }
        否则   → { type:"steer" | "follow_up", message, images }
  → window.__TAURI__.core.invoke("send_command", {sessionId, json})
  → Rust send_command（lib.rs:61）→ AgentBridge::send（agent/mod.rs）
        validate_command_type → ALLOWED_COMMAND_TYPES 白名单
        write_command：锁内 writeln + flush
        若该帧回答了某个审批提示 → approvals::settle + tracker().on_answered
  → omp stdin
```

### 命令为什么必须走 `prompt`

omp 的 `steer` / `follow_up` 帧**跳过命令与技能分发**。所以 `/compact`、`/effort low`、`/skill:<name>` 之类若走这两条，会被模型当普通文本读。`isCommandInvocation` 是唯一判据：

- 首个 token 是已知命令，或
- 草稿**任意位置**出现 `/skill:<name>`（omp 的 `parseSkillInvocation`/`allowsSkillTokens` 规则）。

判定对象是**用户输入的草稿**，在浏览器标注等页面数据合并**之前**。

## 关键节点详解

| 节点 | 位置 | 核心逻辑 | 异常处理 |
|---|---|---|---|
| 路由判定 | `routeSubmit` | 纯函数，五路选择；命令跨所有通道保持 `isCmd` | 无 |
| 帧构造 | `queuedFrame` | 字面量 `{ type: "…" }` 形式 | Rust 有测试扫描 `live.js` 里的字面量形式并与白名单比对 |
| 白名单 | `ALLOWED_COMMAND_TYPES` | `prompt`/`steer`/`follow_up`/`abort`/`set_model`/… 共 30 余项 | 未列出 → `send_command` 拒绝（前端只记日志） |
| "sending" 行 | `QUEUE.sendingEntry` | 每发一条建一行 | 成功/失败后 `_dropSending`；超时只丢行不出注记 |
| 队列快照 | `state.queue` | 只由 `queue_update` / `get_state.queuedMessages` 覆盖 | 前端**从不**本地编辑 |
| omp 回执 | `queue_update` | 文本在队列里出现次数超过发送时的计数即视为已入队 | — |
| 队列编辑 | `remove_queued_message` / `promote_queued_message` | 只允许一条在飞（omp 按**第一条匹配文本**操作） | `removed:false` / `promoted:false` → 显示"already delivered" |
| ⚡ 立刻发送 | `sendQueuedNow` | 先把 follow-up 提升为 steer，再发 id-less `abort` | 已结束 / abort 在飞 / 期间切过标签页 → 跳过 |

## 异常路径

| 异常 | 处理 |
|---|---|
| IPC 交接失败（非超时） | 该标签页仍活跃 → 在转录里落一条注记，注记文本用 `OMP_MARKDOWN.fenceCode` 包裹（围栏比内部反引号更长，防止逃逸成 markdown） |
| IPC 超时 | 只丢 "sending" 行，不报错（omp 可能其实收到了） |
| omp 拒绝（`prompt_result.status === "error"`） | 进入失败气泡 / 重试行路径 → 详见 [会话全生命周期的重试段](会话全生命周期.md) |
| 发送期间切走标签页 | 响应只在活动标签页分发；`_dropSending(origin, id)` 会到该标签页的快照里删行 |
| 队列条目已被 omp 取走 | `removed:false` → "already delivered"，行只能由 omp 的下一份快照移除 |
| 队列编辑期间切换标签页 | ✎ 只在 `removed:true` 之后把文本放回**原队列所在**的标签页 |
| ⚡ 与 Esc 并发 | `userAbortInFlight` 守卫；⛈ 后不再发 abort，避免停掉刚恢复的回复 |

## 队列的两个语义差异（必须分清）

| | steer | follow-up |
|---|---|---|
| omp 何时投递 | 当前工具批次结束时 | agent 本要停止时 |
| 中止后 | 自动恢复 | 等待；按 ↑ 才立刻开跑 |
| 转录表现 | 无气泡，直到 `message_start` 回显 | 同上 |
